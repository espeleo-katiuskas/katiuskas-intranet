## Conventions

- **Keys**: every table has an `id bigint` generated by the database. That id **never leaves the
  API**: a person is always named by `users.login`, and the other resources use their numeric id.
  The join tables (`user_roles`, `activity_participants`) have a composite key.
- **Time**: instants are `timestamptz`; days (joining, leaving, activity date) are `date`. A
  membership period or temporary leave also carries `period`, a `daterange` column *generated* from
  `start_date` and `end_date` (closed on both ends and open at the end if there is no `end_date`),
  over which an `EXCLUDE` constraint prevents overlaps.
- **Money**: `numeric(10,2)`, in euros. In an accounting entry, positive = comes into the account
  and negative = goes out.
- **Derived values that are not stored**: the age category (comes from `birth_date`), the end of a
  license (December 31st of its `year`), the automatic roles (`member`, `former_member`, `board`),
  the stock of each material item (view `material_item_quantities`), the effective type of an
  account, the balance and the last movement of an account, and the running balance of a ledger or
  of the payment list of a distribution.
- **Where the rules live**: whatever PostgreSQL can express with a constraint (`CHECK`, `UNIQUE`,
  foreign keys, `EXCLUDE`, triggers) is in the database, and the tests really use it, without
  simulating it. What depends on several rows or on other tables and does not fit in a constraint is
  checked by the Go service, and is stated in each table (section "Rules outside the database").
- **Files outside PostgreSQL**: the document archive (`LIBRARY_ROOT`), each person's files
  (`USER_FILES_ROOT`), the files of an activity's memoria (`ACTIVITY_RESOURCES_ROOT`) and the
  documents attached to transactions (`TRANSACTION_FILES_ROOT`) are on disk; in the database only
  the metadata of the last two remains (`activity_resources`, `transaction_files`).

## Map of relationships

```
users ──┬─< memberships, membership_leaves, membership_dues, licenses, board_members
        ├─< user_roles >── roles
        ├─< tokens, magic_link_tokens
        ├─< activities (leader) , activity_participants >── activities
        └─< material_movements (recipient and who records it)

activities ──< activity_resources, activity_participants, material_movements
material_items ──< material_movements        (material_item_quantities is a view of the two)
license_types ──< licenses                material_categories ──< material_items

distributions ──┬─< distribution_options
                ├─< distribution_articles ──< distribution_unit_identifiers
                ├─< distribution_units ──< distribution_unit_identifiers
                └─< distribution_payments  >── transactions

accounts ──< accounts (parent_id)         accounts ──< transaction_entries >── transactions
accounts ──< distributions (account_id)
transactions ──< membership_dues, licenses, distribution_payments
```

`A ──< B` means that `B` has a foreign key to `A`. Each table below gives the detail and the
`ON DELETE` of each one.

## People, access and roles

### `users`

Personal data of anyone linked to the club. There is no separate table of sign-in accounts: what a
session can do depends only on the person's roles (`user_roles`), and there are no passwords. The
only required fields when creating one are first name, last name and date of birth.

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | no | identity |
| `first_name` | text | no |  |
| `last_name` | text | no |  |
| `national_id` | text | yes |  |
| `birth_date` | date | no |  |
| `gender` | gender | yes |  |
| `email` | text | yes |  |
| `phone` | text | yes |  |
| `address` | text | yes |  |
| `postal_code` | text | yes |  |
| `city` | text | yes |  |
| `province` | text | yes |  |
| `emergency_contact` | text | yes |  |
| `membership_number` | integer | yes |  |
| `created_at` | timestamptz | no | now() |
| `updated_at` | timestamptz | no | now() |
| `last_login_at` | timestamptz | yes |  |
| `last_login_ip` | text | yes |  |
| `login` | text | no |  |
| `telegram_chat_id` | bigint | yes |  |

Notes on the columns:

- `national_id`: DNI. Unique if present.
- `gender`: Optional. The age category is not stored: it is computed from `birth_date`.
- `email`: One or several, separated by a space. An email cannot belong to two people (checked by
  the service, case-insensitively).
- `phone`: One or several, separated by a space, with no spaces inside each one. A phone cannot
  belong to two people (the service compares digits only).
- `emergency_contact`: Free text; allows several contacts.
- `membership_number`: Assigned automatically, the first time the person joins (the next after the
  highest), and does not change when they leave and come back.
- `last_login_at`: Last time they signed in.
- `last_login_ip`: Source address (`X-Forwarded-For` if there is a proxy in front).
- `login`: The person's only identifier toward the outside: the API never exposes the `id`. It is
  generated on creation (first and last name without accents, joined by a dot, with a numeric suffix
  if it already exists) and only an admin changes it.
- `telegram_chat_id`: Linked Telegram chat. It is cleared if the phone changes or if the bot finds
  out it cannot write to that person.

Constraints:

- primary key (id)
- unique (login)
- unique (national_id)
- unique (telegram_chat_id)
- `membership_number_non_negative`: `membership_number >= 0`

Indexes:

- unique `idx_users_membership_number` sobre `(membership_number)` when `membership_number IS NOT
  NULL`

Rules outside the database:

- That `email` and `phone` are not repeated between people cannot be expressed with a `UNIQUE` (each
  field holds several values); `users.Repository` checks it in `Create` and `Update`.

### `magic_link_tokens`

Single-use sign-in links. The same attempt carries the hash of the link's token and that of a
6-digit code; consuming one consumes the other. The plain value is never stored.

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | no | identity |
| `user_id` | bigint | no |  |
| `token_hash` | text | no |  |
| `code_hash` | text | yes |  |
| `code_attempts` | integer | no | 0 |
| `expires_at` | timestamptz | no |  |
| `created_at` | timestamptz | no | now() |
| `consumed_at` | timestamptz | yes |  |

Notes on the columns:

- `code_attempts`: Failed attempts with the code; past a limit (8) it is no longer accepted, without
  affecting the link.
- `consumed_at`: Use mark. Consuming the link or the code fills it in for both.

Constraints:

- primary key (id)
- unique (token_hash)
- `user_id` → `users(id)`, deleted with it

Indexes:

- `idx_magic_link_tokens_user_id` sobre `(user_id)`

### `tokens`

Sessions. The token is opaque: only its SHA-256 hash is stored, and it can be revoked or given a
different expiry. An impersonation session carries in `impersonated_by` the id of the admin who
opened it.

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | no | identity |
| `user_id` | bigint | no |  |
| `token_hash` | text | no |  |
| `expires_at` | timestamptz | no |  |
| `created_at` | timestamptz | no | now() |
| `revoked_at` | timestamptz | yes |  |
| `last_used_at` | timestamptz | yes |  |
| `last_used_ip` | text | yes |  |
| `last_used_user_agent` | text | yes |  |
| `impersonated_by` | bigint | yes |  |
| `lifetime` | interval | yes |  |
| `role_override` | text[] | yes |  |
| `role_override_until` | timestamptz | yes |  |

Notes on the columns:

- `expires_at` and `lifetime` (migration `00038`): a session expires a while after its *last* use,
  not after it was created. `lifetime` is how long that while is, per token (30 days for an ordinary
  one, 3 hours for one opened through a `local.…` address), and every request made with the token
  sets `expires_at` to `now() + lifetime` in the same statement that records the use. A `NULL`
  lifetime is a fixed expiry that uses do not move: impersonation sessions, which are meant to end
  on their own. An expired or revoked token matches nothing, so a use cannot bring one back. When an
  admin sets the expiry of a session by hand, its lifetime becomes the time from then to that moment
  (so the next use does not undo the change); one in the past ends it and leaves the lifetime alone.
- `role_override` and `role_override_until` (migration `00041`): the roles an admin's session was
  asked to act with and until when (`PUT /auth/role-override`); both set or both `NULL`, at least
  one role. While `role_override_until` is in the future the session's roles are those, not the
  person's own; after it, or once they are put back (both `NULL`), they are the person's own again.
  No role of anybody is changed.
- `last_used_at`: Updated on every request made with the token.
- `last_used_ip`: Source of the last request.
- `last_used_user_agent`: The `User-Agent` header of the last request (migration `00037`), whole but
  cut to 512 characters, set in the same statement as `last_used_ip`: the *last* one, not the first,
  because it describes the same request as the address next to it, and a session lasts weeks, in
  which a browser updates and, if the token is copied elsewhere, a different one shows. The browser
  and operating system are not stored: they are worked out from it when a token is read
  (`tokens.DetectClientFromUA`), so a better parser improves the old rows too.

Constraints:

- primary key (id)
- unique (token_hash)
- `impersonated_by` → `users(id)`, deleted with it
- `user_id` → `users(id)`, deleted with it

Indexes:

- `idx_tokens_user_id` sobre `(user_id)`

### `roles`

Catalog of roles. The system ones (`is_system`) are `admin`, `board`, `member` and `former_member`;
the automatic ones (`is_automatic`) are `member`, `former_member` and `board`, which nobody assigns
by hand. `material` and `money` are seeded but are not system roles: a club that does not want them
can delete them. Any other role an admin creates is just a label.

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | no | identity |
| `name` | text | no |  |
| `description` | text | yes |  |
| `is_system` | boolean | no | false |
| `is_automatic` | boolean | no | false |
| `created_at` | timestamptz | no | now() |

Constraints:

- primary key (id)
- unique (name)

### `user_roles`

Many-to-many relation between people and roles. It only holds the roles assigned by hand: `member`,
`former_member` and `board` are computed on the fly from `memberships` and `board_members` and do
not appear here.

| Column | Type | Null | Default |
|---|---|---|---|
| `user_id` | bigint | no |  |
| `role_id` | bigint | no |  |

Constraints:

- primary key (user_id, role_id)
- `role_id` → `roles(id)`, deleted with it
- `user_id` → `users(id)`, deleted with it

## Members

### `memberships`

Periods of membership. A person may have several, but never overlapping. `period` is computed from
`start_date` and `end_date` (closed on both ends; open at the end if the membership continues).

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | no | identity |
| `user_id` | bigint | no |  |
| `start_date` | date | no |  |
| `end_date` | date | yes |  |
| `end_reason` | text | yes |  |
| `period` | daterange | yes | generated |

Notes on the columns:

- `end_reason`: Reason for leaving, if any.

Constraints:

- primary key (id)
- `user_id` → `users(id)`, deleted with it
- `memberships_user_id_period_excl`: exclusion `(user_id WITH =, period WITH &&)` (never two rows of
  the same person with overlapping periods)
- `end_not_before_start`: `(end_date IS NULL) OR (end_date >= start_date)`

Indexes:

- `idx_memberships_user_id` sobre `(user_id)`

Rules outside the database:

- Two periods of the same person overlap if they share any day: the `EXCLUDE` constraint prevents
  it, not a hand-written check.

### `membership_leaves`

Temporary leaves: a window with a start date and an optional end date (open if still ongoing). It
hangs from the person, not from a specific period; that the window falls within one of that person's
periods is checked by the service.

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | no | identity |
| `start_date` | date | no |  |
| `end_date` | date | yes |  |
| `reason` | text | yes |  |
| `period` | daterange | yes | generated |
| `user_id` | bigint | no |  |

Constraints:

- primary key (id)
- `user_id` → `users(id)`, deleted with it
- `membership_leaves_user_id_period_excl`: exclusion `(user_id WITH =, period WITH &&)` (never two
  rows of the same person with overlapping periods)
- `leave_end_not_before_start`: `(end_date IS NULL) OR (end_date >= start_date)`

Indexes:

- `idx_membership_leaves_user_id` sobre `(user_id)`

Rules outside the database:

- That the leave falls within one of the person's membership periods is checked by
  `memberships.Repository` (`findContainingMembership`), because a `CHECK` cannot see other tables.

|---|---|---|---|
| `id` | bigint | no | identity |

| `year` | integer | no |  |
| `transaction_id` | bigint | no |  |
| `created_at` | timestamptz | no | now() |

Constraints:

- primary key (id)

- `transaction_id` → `transactions(id)`, deleted with it

### `licenses`

Federative licenses. The type comes from the `license_types` catalog. `year` is the year it covers
(a license requested in December usually covers the next one) and it is valid until December 31st of
that year; that date is not stored. `transaction_id` is optional and is the only way to record a
license the club did not collect payment for.

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | bigint | no | identity |
| `user_id` | bigint | no |  |
| `license_type_id` | bigint | no |  |
| `other_detail` | text | yes |  |
| `issued_date` | date | no |  |
| `created_at` | timestamptz | no | now() |
| `year` | integer | no |  |
| `transaction_id` | bigint | yes |  |

Notes on the columns:

- `other_detail`: Required if the type is "Otra" and forbidden for any other (validated by the
  service).
- `issued_date`: When it was obtained; it need not fall in `year`.

Constraints:

- primary key (id)
- `license_type_id` → `license_types(id)`
- `transaction_id` → `transactions(id)`
- `user_id` → `users(id)`, deleted with it

Indexes:

- `idx_licenses_user_id` sobre `(user_id)`

Rules outside the database:

- A license is only assigned to someone who was a member at some point of its `year`, and if it
  carries `transaction_id` the transaction has to have an entry on an `allows_licenses` account: the
  service checks both.

the database and not in a Go enum so it can be extended with an `INSERT`.

| Column | Type | Null | Default |

| `id` | bigint | no | identity |
| `name` | text | no |  |

Constraints:

- primary key (id)
- unique (name)

## Distributions

### `accounts`

## Functions, triggers and extensions

- **Extension `btree_gist`** (migration 00001): makes possible the `EXCLUDE USING gist` constraint
  that prevents overlapping periods in `memberships`, `membership_leaves` and `board_members`.
- **`check_transaction_balance()`** and the constraint trigger `transaction_entries_balance` on
  `transaction_entries`: after the entries of a transaction are written, it checks that there are at
  least two and that they sum to exactly zero (`check_violation`). It is `DEFERRABLE INITIALLY
  DEFERRED`, so it runs at `COMMIT` and not row by row, and it does not complain when the whole
  transaction is being deleted.
- **`check_entry_account_is_leaf()`** and the trigger `transaction_entries_account_is_leaf`
  (migration 00033): rejects an entry on an account that has child accounts
  (`account_has_children`).
- **`check_parent_account_has_no_entries()`** and the trigger `accounts_parent_has_no_entries`
  (migration 00033): rejects creating an account under another that already has entries, or moving
  one to it (`parent_has_entries`).
- **`account_effective_type(id)`** (migration 00034): the type of an account or, if it has none,
  that of its parent account, and so on upwards (null if nobody has one). The type-dependent rules
  and the account listing use it.

  `club_info_items` (the club's data is entered from `/admin`, so none of it is in the repository:
  the home page shows nothing until then). The first admin is created with `make seed-admin`.

## Migrations

Numbered and applied in order with goose (`make migrate-up`; the applied version is in
`goose_db_version` and `GET /admin/status` shows it). A migration that has been published is not
edited: a new change is another migration. The tests of each package that touches PostgreSQL migrate
a test database (`TEST_DATABASE_URL`) and give each test its own transaction, which is rolled back
at the end; that database has to be recreated when a new migration appears.
